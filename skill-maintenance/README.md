# skill-maintenance

## 诞生背景

技能被多个"路过的"智能体各改一刀，是真实的腐化模式：每个修改者只带着自己当下任务的视角，只追加不整合，技能越改越臃肿、越改越自相矛盾。本机制针对的是**维护质量**（技能被改坏），而不是**调用质量**（工作者在具体任务上用不好技能）；后者只通过把判断规则沉淀进 SKILL.md 间接改善，调用时咨询不在本期范围。

三条核心洞察支撑整个设计：智能体是无状态的——维护者的身份与记忆应落在技能目录的持久化文件里，而不是进程里；批处理本身就是防堆砌的机制——攒一批反馈才能看出"五条抱怨是同一个根因"，写一条好规则替代五个补丁；不验证行为、验证产物——提示词约束永远是软的，约束必须落成可核对的产物（轮报告、技能地图哈希、变更日志、快照）。

当时评估过并放弃的备选：常驻维护者进程（无状态智能体无法用进程承载记忆）、拆成三个技能（同一协议多处维护，等于新增漂移源）、技术强制（文件权限/git hook 与载体绑定，覆盖不了全部写入路径）、把 skill-creator 搬进本技能（等于改名 fork，外部同步会覆盖副本，且治理技能自身第一个爆长度预算）。

讨论结论：**出生有仪式、服役只提案、修改走轮次**。本技能是规则的源头，出生即 `stage: governed`（元治理特例）；它同时吃自己的狗粮——本 README 与账本、提案区、轮次区都由它自己的 `init_ledger.py` 初始化。

## 技能边界

- 状态: ratified（owner 2026-10-24 批准；approval_id: owner-2026-10-24-boundary）
- 做什么：为需要长期维护的技能提供全生命周期治理——创建出生（§C：init 先行、边界先行、委托 skill-creator、核验、记录）、使用反馈（§A：写法提案、边界上报（R30）、critical 判据、两条禁令）、维护轮（§B：12 步固定流程，裁决四词汇 + 锚点整合）、收养（§C 收养路径：结构收养 + 拟边界交 owner）；维护 README/账本/提案区/轮次区等维护面，并提供 `init_ledger.py` 与 `check_skill.py` 两个确定性脚本。
- 明确不做什么（负空间）：**不含调用时咨询**（不在工作者执行任务时提供建议、委托或代执行）；**不含跨技能全局审计**（本期不实现，只预留机器可扫描的格式，由人每月抽查代替）；不替代 skill-creator 的创作与评估方法论（委托而非 fork）；不直接改代码、不做内容创作；不治理一次性实验技能（走原生 skill-creator 轻量路径）。
- 边界判例（3 条，场景 → 算/不算 → 理由）：

| 场景 | 判断 | 理由 |
|---|---|---|
| 用户要求直接修改受治理技能的 SKILL.md 或脚本 | 不算 | 治理期只有维护者经维护轮写入（§B R14 / 不变量 I1）；worker 只能提交提案 |
| 用户要求给技能增加"调用时咨询/代执行"能力 | 不算 | 负空间已明确不含调用时咨询；扩张须 owner 批准并走三处同步（V9） |
| 用户报告技能指引有歧义、导致任务偏离 | 算 | 属 §A 偏离提案与 §B 分诊范围；按维护轮裁决处理 |

## 使用场景

- 典型场景：
  - **创建**：用户要"创建一个长期维护的技能 X" → 走 §C 五步，出生即 `stage: incubating`。
  - **反馈**：工作者使用技能时发生偏离（绕步、重新解释、靠猜）→ 按维护通道在 `proposals/open/<提案ID>/REPORT.md` 写提案，不阻塞任务；任务失败或产出错误交付物标 critical。
  - **维护**：提案攒够或人工发起 → 唤起一次性维护者 → 按 §B 执行一轮 12 步，按锚点整合修改并留下可核对的产物。
  - **收养**：要修改一个无账本技能（轻量出生）→ 先走 §C 收养路径，由 owner 或维护者执行 `init_ledger.py --adopt`，再按常规维护。
- 边缘场景：同一批提案跨多个技能 → 本期无协调机制，交人决策；维护轮中发现未经流程的直接改动 → 先走审计兜底，再进常规维护。
- 不该触发的场景：直接写代码或改脚本、内容创作、一次性实验技能、只是使用而不修改某个技能。
